# JobReady — описание программы

Состояние на 8 ноября 2026 года.

---

## 1. Назначение

JobReady — веб-тренажёр для подготовки к собеседованиям в IT. Пользователь проходит пробное интервью с AI-интервьюером, получает разбор своих ответов и персональный план подготовки, прорабатывает слабые темы и повторяет интервью.

Целевая аудитория — русскоязычные специалисты (Product Designer, Frontend, Backend, QA, Product Manager, системные аналитики) уровней от Junior до Team Lead, которые готовятся к собеседованию.

Основные возможности (полный замысел):

1. Вход по номеру телефона с подтверждением кодом из SMS.
2. Выбор цели подготовки: первое собеседование, проверка знаний, разбор неудачного собеседования, подготовка к конкретной вакансии.
3. Настройка интервью: профессия, грейд, тип (HR, техническое, смешанное).
4. Пробное интервью в формате чата с AI-интервьюером.
5. Разбор интервью: общая оценка, метрики, сильные и слабые стороны, разбор каждого вопроса, сравнение со средним по рынку.
6. План подготовки по дням на основе слабых мест.
7. Проработка отдельных тем с оценкой нового ответа.
8. История интервью и проработок.

Что из этого уже работает, а что запланировано, описано в разделах 9 и 11.

## 2. Архитектура

Программа состоит из двух частей — фронтенда и бэкенда — и использует две внешние системы.

```
┌────────────────────────┐        HTTP / JSON, SSE         ┌──────────────────────────┐
│  Браузер пользователя  │ ──────────────────────────────▶ │  Бэкенд (FastAPI)        │
│                        │      cookie сессии (httpOnly)   │  http://localhost:8000   │
│  Фронтенд (Next.js)    │ ◀────────────────────────────── │                          │
│  http://localhost:3000 │                                 │  ┌────────────────────┐  │
└────────────────────────┘                                 │  │ База данных        │  │
                                                           │  │ SQLite / PostgreSQL│  │
                                                           │  └────────────────────┘  │
                                                           └──────┬────────────┬──────┘
                                                                  │            │
                                                     HTTPS        │            │  (запланировано)
                                                                  ▼            ▼
                                                     ┌────────────────┐  ┌──────────────┐
                                                     │ GigaChat API   │  │ SMS-провайдер│
                                                     │ (Сбер)         │  │              │
                                                     └────────────────┘  └──────────────┘
```

- **Фронтенд** отвечает только за интерфейс: показывает экраны, отправляет действия пользователя на бэкенд и отображает ответы.
- **Бэкенд** содержит всю логику: авторизацию, ход интервью, работу с базой данных и языковой моделью. Ключ доступа к GigaChat хранится только на бэкенде и никогда не попадает в браузер.
- **База данных** хранит пользователей, коды подтверждения, сессии, интервью и переписку.
- **GigaChat** — языковая модель Сбера, которая генерирует вопросы и реплики интервьюера.

Фронтенд может работать и без бэкенда — в демо-режиме на заранее подготовленных данных (моках). Режим определяется переменной `NEXT_PUBLIC_API_URL`: если она задана, фронтенд обращается к бэкенду.

## 4. Сценарий работы пользователя

1. **Вход.** Пользователь вводит имя и номер телефона → получает 4-значный код → вводит его. Если пользователь новый, он создаётся автоматически.
2. **Цель.** На экране «Главная» выбирает цель подготовки.
3. **Настройка интервью.** Выбирает профессию, грейд и тип интервью, нажимает «Начать интервью».
4. **Интервью.** GigaChat составляет 10 вопросов. Интервьюер здоровается и задаёт первый вопрос. На каждый вопрос: ответ пользователя → уточняющий вопрос интервьюера по этому ответу → второй ответ → короткая связка и следующий вопрос. Любой вопрос можно пропустить. Слева показывается текущий вопрос и прогресс «N/10 вопросов».
5. **Завершение.** После последнего вопроса интервью завершается, появляется кнопка «Посмотреть результаты».
6. **Результаты, план, проработка тем, история** — экраны свёрстаны, но пока показывают демонстрационные данные (см. раздел 11).

### 5.3. Адаптивность

Интерфейс свёрстан по макетам из Figma для трёх ширин:

- до 768 px — телефон: одна колонка, шапка с меню-«бургером»;
- 768–1023 px — планшет: сетки в 2–3 колонки;
- от 1024 px — десктоп: боковое меню слева, двухколоночные экраны.

### 5.4. Взаимодействие с бэкендом

Все обращения к бэкенду собраны в файле `lib/api.ts`:

- `api` — чтение данных для страниц (результаты, план, темы);
- `auth` — запрос кода, повторная отправка, проверка кода, выход;
- `interviews` — создание интервью, получение состояния, отправка ответа, пропуск вопроса.

Запросы из браузера отправляются с cookie сессии (`credentials: "include"`). Ошибки бэкенда приходят в едином формате `{"detail": {"message": "..."}}`, и фронтенд показывает пользователю текст из поля `message`.

**Потоковые ответы интервьюера.** Ответ кандидата отправляется POST-запросом, а реплика интервьюера приходит потоком в формате SSE (Server-Sent Events). Фронтенд читает поток по частям и дописывает текст в сообщение чата по мере поступления — пользователь видит, как интервьюер «печатает». Логика чата вынесена в хук `components/interview/use-interview.ts`; в нём два варианта: работа с бэкендом и демо-режим на моках.

```

    services/
      auth.py            коды из SMS и сессии

      interview_prompts.py  тексты запросов к модели (промпты)
      llm/               доступ к языковой модели: общий интерфейс + GigaChat
```

Код разделён на слои: **маршруты** принимают HTTP-запросы и возвращают ответы, **сервисы** содержат бизнес-логику, **модели** описывают таблицы базы данных, **схемы** описывают формат данных API. Ответы API формируются в стиле camelCase, как принято во фронтенде, а в Python-коде используется snake_case — преобразование происходит автоматически.

### 6.3. Авторизация по SMS

**Алгоритм:**

1. Пользователь отправляет имя и телефон (`POST /auth/sms`).
2. Номер приводится к единому виду `+7XXXXXXXXXX` — номера `8 999…`, `+7 (999)…` и `9991234567` считаются одним и тем же.
3. Бэкенд генерирует случайный 4-значный код, сохраняет в базе его подпись (HMAC-SHA256 с секретным ключом), а не сам код, и отправляет код в SMS.
4. Пользователь вводит код (`POST /auth/verify`). При совпадении код помечается использованным, при необходимости создаётся пользователь, создаётся сессия.
5. Бэкенд устанавливает cookie `session` со случайным токеном сессии. Cookie имеет флаги `HttpOnly` (недоступна для JavaScript на странице) и `SameSite=Lax`, а в продакшене — `Secure`. В базе хранится не сам токен, а его хеш SHA-256.
6. При каждом запросе к защищённым эндпоинтам бэкенд находит сессию по токену из cookie и определяет пользователя.

**Защита от перебора и злоупотреблений:**

| Правило | Значение |
|---|---|
| Время жизни кода | 5 минут |
| Попыток ввода на один код | 5, затем нужен новый код |
| Повторная отправка | не раньше чем через 60 секунд |
| Кодов на один номер | не больше 5 в час |
| Время жизни сессии | 30 дней |
| Код повторно | не принимается — работает один раз |

**Отправка SMS.** Сейчас используется заглушка: код печатается в консоль сервера (`[SMS → +79990000001] JobReady: код для входа 1234`). Настоящий SMS-провайдер подключается отдельным классом с тем же интерфейсом (см. раздел 11).

### 6.4. Пробное интервью

**Создание интервью** (`POST /interviews`):

1. Проверяются профессия, грейд, тип и цель по справочникам.
2. GigaChat получает запрос составить 10 вопросов с учётом профессии, грейда, типа интервью и цели пользователя. Ответ ожидается в виде JSON-массива; если модель ответила в другом формате, вопросы извлекаются построчно. Если вопросов меньше пяти, делается вторая попытка; если и она неудачна, пользователь получает сообщение об ошибке.
3. Создаётся запись интервью, первым сообщением сохраняется приветствие интервьюера с первым вопросом. Цель сохраняется в профиле пользователя.

**Ход интервью.** Порядок интервью контролирует бэкенд, а не модель. Модель отвечает только за тексты реплик. Это делает длину интервью и прогресс предсказуемыми.

Для каждого интервью хранятся номер текущего вопроса и число уже заданных уточнений. На каждый ответ кандидата бэкенд выбирает один из трёх шагов:

| Шаг | Когда | Что делает интервьюер |
|---|---|---|
| Уточнение | по текущему вопросу ещё не было уточнения | GigaChat задаёт один уточняющий вопрос по ответу кандидата (просит конкретику, пример, личную роль или результат) |
| Следующий вопрос | уточнение уже было, вопросы ещё остались | GigaChat пишет короткую нейтральную связку, к ней добавляется следующий вопрос из плана |
| Завершение | это был ответ на последний вопрос | фиксированный текст о завершении, интервью получает статус «завершено» |

**Промпты.** Тексты запросов к модели вынесены в файл `services/interview_prompts.py`. Системная инструкция задаёт роль опытного интервьюера, обращение на «ты», короткие реплики (1–2 предложения) и запрещает оценивать ответы и подсказывать правильный ответ во время интервью — разбор пользователь получает после. Модель получает всю историю переписки, поэтому уточнения опираются на сказанное ранее.

**Защита от ошибок модели.** Модель иногда нарушает инструкцию «напиши связку без вопросов» и задаёт собственный вопрос — тогда в чате оказалось бы два вопроса подряд. Поэтому связка проверяется перед показом: если в ней есть вопросительный знак или она слишком длинная, вместо неё используется нейтральное «Понял, спасибо.». Этот случай был обнаружен при проверке на реальной модели.

**Потоковая передача (SSE).** Ответ на `POST /interviews/{id}/messages` — поток событий, каждое в формате `data: {json}`:

- `{"type": "delta", "text": "..."}` — очередной кусок реплики интервьюера;
- `{"type": "done", "state": {...}}` — реплика сохранена, передаётся новое состояние интервью;
- `{"type": "error", "message": "..."}` — ошибка, ничего не сохранено.

Ответ кандидата и реплика интервьюера сохраняются в базу вместе и только после того, как реплика получена полностью. Если связь оборвалась или модель вернула ошибку, база не меняется и пользователь может отправить ответ ещё раз (во фронтенде для этого есть кнопка «Отправить ещё раз»). В истории не остаётся обрывков и «повисших» ответов без реакции.

### 6.5. Модуль работы с языковой моделью

Модуль `services/llm/` описывает общий интерфейс с методами: получить ответ целиком, получить ответ потоком, получить список моделей (используется для проверки связи). Реализация для GigaChat:

- использует официальную библиотеку Сбера `gigachat`;
- получает и обновляет токен доступа автоматически по ключу авторизации;
- переводит технические ошибки в понятные сообщения: неверный ключ, не найден сертификат, превышена квота, нет связи;
- для проверки подключения есть консольная команда `python -m app.services.llm.check` и адрес `/health/llm`.

## 7. База данных

### 7.1. СУБД и миграции

- При разработке используется **SQLite** — база хранится в одном файле `backend/jobready.db` и не требует установки сервера.
- Для продакшена предусмотрен **PostgreSQL 17**, конфигурация запуска — `backend/docker-compose.yml`. Переход выполняется изменением одной строки `DATABASE_URL`.
- Код написан так, чтобы работать с обеими СУБД: например, JSON-поля в PostgreSQL хранятся как `JSONB`, в SQLite — как `JSON`.
- Схема базы изменяется только через **миграции Alembic** (`backend/alembic/versions/`). Сейчас их три: начальные таблицы; коды SMS и сессии; поля прогресса интервью. Команда `alembic upgrade head` приводит любую базу к актуальной схеме.

### 7.2. Таблицы

**users — пользователи**

| Поле | Тип | Описание |
|---|---|---|
| id | UUID, PK | идентификатор |
| name | строка | имя |
| phone | строка, уникальное | телефон в формате +7XXXXXXXXXX |
| goal | строка, может быть пустым | цель подготовки |
| created_at | дата-время | дата регистрации |

**sms_codes — коды подтверждения**

| Поле | Тип | Описание |
|---|---|---|
| id | UUID, PK | идентификатор |
| phone | строка, индекс | номер телефона |
| name | строка | имя из формы входа (для нового пользователя) |
| code_hash | строка | HMAC-подпись кода (сам код не хранится) |
| attempts | целое | число неудачных попыток ввода |
| expires_at | дата-время | когда код перестаёт действовать |
| used_at | дата-время, может быть пустым | когда код был использован |
| created_at | дата-время | когда код был отправлен |

**sessions — сессии входа**

| Поле | Тип | Описание |
|---|---|---|
| id | UUID, PK | идентификатор |
| token_hash | строка, уникальное | SHA-256 токена из cookie |
| user_id | UUID, FK → users | пользователь |
| expires_at | дата-время | окончание сессии |
| created_at | дата-время | время входа |

**interviews — интервью**

| Поле | Тип | Описание |
|---|---|---|
| id | UUID, PK | идентификатор |
| user_id | UUID, FK → users | владелец |
| profession, grade, type | строки | параметры интервью |
| goal | строка, может быть пустым | цель подготовки |
| status | строка | `in-progress` или `finished` |
| questions | JSON | список вопросов, составленный моделью |
| current_question | целое | номер текущего вопроса (с нуля) |
| followups | целое | сколько уточнений задано по текущему вопросу |
| created_at, finished_at | дата-время | начало и окончание |

**interview_messages — сообщения интервью**

| Поле | Тип | Описание |
|---|---|---|
| id | UUID, PK | идентификатор |
| interview_id | UUID, FK → interviews | интервью |
| role | строка | `ai` (интервьюер) или `user` (кандидат) |
| text | текст | текст сообщения |
| created_at | дата-время | время, по нему сообщения упорядочиваются |

**interview_results — разборы интервью** *(таблица создана, заполнение запланировано)*

| Поле | Тип | Описание |
|---|---|---|
| interview_id | UUID, PK, FK → interviews | интервью |
| overall | число | общая оценка |
| payload | JSON | полный разбор: метрики, сильные и слабые стороны, разбор вопросов |
| created_at | дата-время | время разбора |

**plans — планы подготовки** *(таблица создана, заполнение запланировано)*

| Поле | Тип | Описание |
|---|---|---|
| id | UUID, PK | идентификатор |
| user_id | UUID, FK → users | пользователь |
| interview_id | UUID, FK → interviews, может быть пустым | интервью, по которому составлен план |
| payload | JSON | дни и темы плана |
| created_at | дата-время | время составления |

### 7.3. Связи

```
users ──1:N── sessions
users ──1:N── interviews ──1:N── interview_messages
                    │
                    └──1:1── interview_results
users ──1:N── plans ──N:1── interviews
sms_codes — связаны с пользователем по номеру телефона (до регистрации пользователя ещё нет)
```

При удалении пользователя удаляются его сессии, интервью и планы; при удалении интервью — его сообщения и разбор.

Результаты работы модели (разбор, план) хранятся целиком в JSON-полях в том же виде, в каком их отдаёт API. В отдельные колонки вынесены только данные, по которым нужен поиск или сортировка (например, общая оценка).

## 8. Интеграция с GigaChat

- **Доступ.** Проект создан в личном кабинете Сбера (developers.sber.ru → Studio → GigaChat API), тариф для физических лиц с бесплатной квотой токенов. Ключ авторизации хранится в `backend/.env`.
- **Сертификат.** Серверы GigaChat используют сертификат российского удостоверяющего центра Минцифры, которого нет в стандартных хранилищах. Корневой сертификат «Russian Trusted Root CA» (действует до 2032 года) скачан с Госуслуг и лежит в `backend/certs/`. Он применяется только к запросам к GigaChat и не устанавливается в систему.
- **Модели.** Аккаунту доступны чат-модели GigaChat-2, GigaChat-2-Pro, GigaChat-2-Max, GigaChat-3-Lightning, GigaChat-3-Pro, GigaChat-3-Ultra. Все проверены. Используется лёгкая модель **GigaChat-2** — она расходует меньше всего бесплатной квоты; модель меняется одной настройкой.
- **Адрес API.** Используется `https://gigachat.devices.sberbank.ru/api/v1`. На адресе `api.giga.chat`, который библиотека использует по умолчанию, потоковые ответы приходили одним куском в конце (ответ из 3000 символов — целиком через 3,7 с), а на выбранном адресе первые слова приходят примерно через 0,5 с.

## 10. Тестирование

### 10.1. Автоматические тесты

На бэкенде 40 автотестов (pytest). Каждый тест работает на отдельной временной базе данных; вместо отправки SMS и обращений к GigaChat используются заменители, поэтому тесты не тратят квоту и не зависят от сети.

| Область | Что проверяется |
|---|---|
| Общие эндпоинты | работа сервера и базы, формат ответов (camelCase, как ожидает фронтенд), проверка связи с моделью |
| Авторизация | полный вход и выход; любой формат номера — один пользователь; неверный код и блокировка после 5 попыток; код работает один раз; код устаревает через 5 минут; повторная отправка не раньше 60 секунд с сохранением имени; лимит 5 кодов в час; истечение сессии через 30 дней; проверка входных данных |
| Интервью | доступ только после входа; создание интервью и учёт цели в промпте; повтор при неверном формате вопросов; потоковое уточнение и сохранение; переход к следующему вопросу; замена связки с вопросом; полное интервью из 10 вопросов (41 сообщение) и запрет ответа после завершения; ошибка модели не сохраняет ничего; пропуск вопросов; пустой ответ; чужое интервью недоступно; разбор ответа модели в разных форматах |
| Настройки | пустой ключ считается незаданным; сообщение об отсутствующем сертификате |

### 10.2. Проверка вручную

Фронтенд проверен компилятором TypeScript и линтером ESLint. Сценарии проверены в браузере на работающих фронтенде, бэкенде и реальном GigaChat:

- вход: отправка кода, неверный код («Неверный код, осталось попыток: 4»), правильный код и переход к выбору цели; cookie сессии недоступна для JavaScript;
- интервью: создание (вопросы составлены моделью), уточняющие вопросы по ответам, переход к следующему вопросу, потоковое появление текста, сохранение переписки после перезагрузки страницы, пропуск вопроса, прогресс «4/10 вопросов».

## 11. Планируемая разработка

### 11.1. Разбор интервью (следующий этап)

После завершения интервью GigaChat анализирует всю переписку и формирует разбор в формате, который уже отображает экран «Результаты»:

- общая оценка по шкале 0–10 и краткий вывод;
- метрики: структура ответа, логика, уверенность;
- сильные и слабые стороны;
- разбор каждого вопроса: оценка, что было не так, как улучшить.

Разбор сохраняется в таблицу `interview_results`. Модель должна вернуть строго структурированный JSON, который проверяется по схеме; при ошибке формата запрос повторяется. Для разбора, вероятно, понадобится более сильная модель (GigaChat-2-Pro / Max или GigaChat-3) — выбор будет сделан после сравнения моделей на реальных интервью.

**Среднее по рынку.** Пока у сервиса нет статистики, будут использоваться фиксированные эталонные значения по профессии и грейду; когда накопятся данные, они будут заменены реальной агрегацией по базе.

### 11.2. План подготовки и проработка тем

- На основе слабых мест из разбора модель составляет план по дням с темами; план сохраняется в таблицу `plans`.
- На экране темы пользователь отвечает заново, модель оценивает новый ответ, сравнивает с прежним и показывает, что улучшилось, а что нет (экран «Результат проработки» уже свёрстан).
- Последний день плана — повторное интервью.

### 11.3. История

Экран «История» будет показывать реальные интервью и проработки пользователя с оценками и датами.

### 11.4. Доступ и данные пользователя

- Страницы приложения будут доступны только после входа; без сессии — переадресация на экран входа.
- В боковом меню будут показываться имя пользователя и его прогресс вместо демонстрационных данных.
- Кнопка «Выйти» будет вызывать выход на бэкенде.

### 11.5. Отправка SMS

Подключение реального SMS-провайдера (например, SMS.ru или SMSC). SMS платные — обычно несколько рублей за сообщение. Провайдер добавляется отдельным классом в `services/sms.py` без изменения логики авторизации.

### 11.6. Голосовой ввод

Кнопка микрофона в поле ответа уже есть в интерфейсе. Планируется распознавание речи (speech-to-text), чтобы отвечать голосом, как на реальном собеседовании.

### 11.7. Развёртывание

- переход на PostgreSQL;
- размещение фронтенда и бэкенда на сервере с HTTPS;
- режим `APP_ENV=prod`: Secure-cookie, обязательный уникальный `SECRET_KEY`;
- перевыпуск ключа GigaChat для продакшена.

### 11.8. Прочее

- выбор модели GigaChat для каждой задачи по итогам сравнения качества;
- иллюстрации в двойном разрешении для экранов высокой плотности (Retina).

## 12. Известные ограничения

- SMS не отправляются: код при разработке выводится в консоль сервера.
- Экраны «Результаты», «План», «Проработка темы», «История» показывают демонстрационные данные.
- Страницы приложения открываются без входа; в боковом меню отображается демонстрационный пользователь.
- Бесплатная квота GigaChat ограничена; при её исчерпании интервью не сможет продолжаться (пользователь увидит понятное сообщение об ошибке).
- Ход интервью фиксирован: одно уточнение на каждый вопрос, независимо от полноты ответа.

## 13. Запуск

**Бэкенд** (в папке `backend`):

```
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env          (затем заполнить ключ GigaChat и путь к сертификату)
alembic upgrade head
fastapi dev app/main.py          → http://localhost:8000, документация — /docs
```

**Фронтенд** (в папке `frontend`, нужен Node.js 20.9+):

```
npm install
(в frontend/.env.local указать NEXT_PUBLIC_API_URL=http://localhost:8000)
npm run dev                      → http://localhost:3000
```

**Тесты:** `pytest` в папке `backend`.
